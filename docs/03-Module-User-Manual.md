# 03 — Module User Manual

[Documentation index](README.md) · Previous: [System Architecture](02-System-Architecture.md) · Next: [Database Design](04-Database-Design.md)

This manual describes how to operate the delivered modules. Validation messages quoted in
*italics* are the exact texts returned by the server code. Screens are reached from the left-hand
sidebar; the menu titles below are those created by `npm run db:setup` (`prisma/seed.ts` and the
seed scripts in `nexuscore-backend/scripts/`). An administrator can rename or reorder menu items,
so an installation may differ.

> **Not verified in a browser during this handover.** Workflows were documented from the screen and
> API source code and the automated tests. Screenshots are not included because none were captured
> from a verified running system. Confirm each workflow during acceptance testing
> ([10 — Handover Checklist](10-Client-Handover-Checklist.md)).

## 1. Common conventions

### 1.1 Signing in

1. Open the application URL; you are redirected to the sign-in page (`/login/v1`).
2. Enter your e-mail and password. There is no account lockout after failed attempts; instead the
   sign-in endpoint is rate-limited to **10 attempts per minute**.
3. A new account, or one whose password was set by an administrator, must **change its password at
   first sign-in** (`User.mustChangePassword`). Until then every other screen answers *Password change
   required*. New passwords must be at least **6 characters** (`ChangePasswordDto`).
4. After sign-in, URLs take the form `/<company-slug>/<screen>`, e.g. `/acme/legacy-erp/work-orders-list`.
5. *Forgot password* sends a reset link by e-mail (requires SMTP — see
   [06 — Installation](06-Installation-Guide.md)). The response never reveals whether the account exists.

Sign-in errors: *Invalid credentials*, *Account is deactivated*, and for trial companies a 403
*TRIAL_EXPIRED* once the trial end date has passed.

### 1.2 Screen layout

- **List screens** (`…-list`) show records in a grid with search, column filters, paging and, where
  available, *Export* and *Print*. Opening a row opens the record in a workspace tab, so several
  records can be open side by side.
- **Record screens** have a header section and tabbed detail grids. Use *New*, *Save* and *Delete*
  from the toolbar. Grids support adding, editing and deleting lines.
- **Lookups** (Current Account, Inventory Card, Work Order, Style Card …) open a search dialog.
  Lookups only show records of your own company.
- **Actions you lack permission for** are refused by the server with *Insufficient permissions*
  (HTTP 403) even if the button is visible.

### 1.3 Approvals

Approval is configured per screen in **Legacy ERP → General Settings** (Approval Configuration).
For a screen with *approval required*:

1. Save the record, then choose **Submit for Approval**.
2. A user with `approval:approve` / `approval:reject` uses **Approve** or **Reject** (a rejection
   reason is mandatory: *A rejection reason is required.*).
3. You cannot approve your own submission unless *self approval allowed* is set for that screen
   (*You cannot approve or reject your own submission.*).
4. *Is Approved* can never be typed directly (*Is Approved cannot be set directly — use Approve or
   Unapprove.*). An approved document must be **Unapproved** before it can be changed.

### 1.4 Company isolation

Each NexusCore company is linked to one legacy ERP company. All Legacy ERP screens only show and
accept that company's data. If your company has no link you will see *This company is not linked to
a legacy ERP company. Ask an administrator to set the mapping.* Records of another company behave as
if they do not exist ("not found"). Some reference masters (processes, quality types, size sets,
item groups, unit sets) are deliberately shared by all companies.

## 2. Legacy ERP — master data

| Screen (menu) | Purpose | Notes |
|---|---|---|
| Warehouses | Warehouses and their parameters | Warehouse Parameters screen sets module parameters per warehouse |
| Current Account | Customers, suppliers, subcontractors (FI_Account) | Tabs: forex rates, addresses, contacts, explanations, guarantors, bank accounts, inventory attributes, documents/pictures |
| Yarn Cards / Fabric Cards / Customer Define Trims (Trim Cards) / Trim Inventory Cards | Material masters | Attachments supported; Fabric Card yarn recipe; codes are generated by the server |
| Inventory Card List | Unified inventory card list with stock value | Stock value rules are covered by `test:stock-value` |
| Master lookups (Fab Type, Group Code, Finish GSM, Dye Type, Composition, Subcontract Type, Subcontract Receipt) | Simple code/name lists | One screen (`master-lookup?key=…`) |
| Sizes, Unit Sets | Size sets and units with conversion | Shared across companies |

**Typical procedure (any master):** open the list → *New* → fill the mandatory fields → *Save*.
Duplicate codes are refused (*<field> already exists* / HTTP 409).

## 3. Legacy ERP — purchasing and contracts

### 3.1 Purchase Order (1) and Subcontract Order (3)

1. *1 - Purchase Order* (or *3 - Subcontract Order*) → *New*.
2. Select the Current Account, warehouse and dates; add lines (inventory item or service, variant,
   quantity, price). Service lines need a service (*A service is required*), item lines an item
   (*An inventory item is required*) and, for variant items, a variant (*A variant is required*).
3. Lines can be linked to a Work Order line of your company (*Work Order line is not one of your
   company's* otherwise).
4. *Save*. If the screen requires approval, use *Submit for Approval*; the status cannot be set
   directly (*This screen requires approval — use the Approve/Reject actions instead of setting
   status directly.*).

### 3.2 Contracts

*1 - Purchase Contract* and *2 - Sale Contract* (`contracts-list`) record contract headers, lines and
attachments for a Current Account.

## 4. Legacy ERP — manufacturing

### 4.1 Work Order

1. *Work Order* → *New*. The next number is proposed by the server (`/work-orders/next-code`).
   A Style Card is mandatory (*styleCardId is required*) and must belong to your company.
2. **Style Info** tab: style lines. **Manufacturing Quantities**: colour × size breakdown per line.
3. **BOM** tabs (Fabric / Trim / Ornament / Process): material lines. *Transfer from Style Card* and
   the *Transfer … Details* actions copy BOM lines from the linked PLM Style Card.
4. **Initial Cost**: optionally link a Costing Sheet of your company (*Initial Cost must be one of
   your company*). *(Uncommitted work in progress at audit time — see
   [08](08-Testing-and-Limitations.md).)*
5. Explanation, Activities and Expenses tabs hold free-text and cost lines.
6. *Order Form* prints the Work Order order form report.

Duplicate numbers are refused (*A work order already exists with this number.*).

### 4.2 Fabric / Trim / Yarn Requirements

Menu: *Fabric/Trim/Yarn Requirements → Fabric / Trim / Yarn Requirements*.

1. Select a Work Order and the requirement type.
2. **Calculate** builds requirement lines from the BOM and quantities; edit if needed and save.
3. **Lock** freezes the requirement (`requirements:lock`). While locked, Calculate/Save/Delete are
   refused (*… Requirement is locked …*) unless you hold `requirements:unlock`.
4. **Unlock** requires `requirements:unlock` (*You do not have permission to unlock Requirements.*).
5. Lines using *Fix Quantity* take their quantity from the Style Card BOM and must be changed there.

Planning screens (*Fabric Planning*, *Yarn Planning*, *Trim Planning*, *Yarn Recipe*) present the
requirements for planning and recipe usage.

### 4.3 Order Manufacturing Entry

Records manufacturing quantities per process on the route of a work order, plus price contracts.
Processes come from the style's route card. Covered by `test:om-route` and `test:om-entry-report`.

### 4.4 Cutting Card

From a Work Order: cutting card detail and entries with sizes (`cutting-cards:*` permissions).

### 4.5 Cutting Orders (BPM)

Separate cutting-order module with rolls, marker plans, batches, cut pieces, approval submission and
audit trail (`/api/v1/cutting-orders`). Workflow stages are seeded as *Draft → Pending Approval →
Approved → In Progress → Quality Check → Completed / Cancelled*.

## 5. Legacy ERP — inventory

### 5.1 Inventory Receipts

Menu: *Inventory Receipts* → one entry per receipt type:

| Code | Receipt type | Code | Receipt type |
|---|---|---|---|
| 2 | Purchase Receipt | 140 | Manufacture Send Receipt |
| 122 | Purchase Return | 40 | Manufacture Return Receipt |
| 16 | Counting Stock Receipt | 10 | Outside Manufacture Receipt |
| 101 | Counting Stockovers Receipt | 132 | Special Purpose (Outflow) Receipt |
| 17 | Warehouse Transfer Receipt | 18 | Special Purpose (Inflow) Receipt |
| 11 | Outside Process Receive Receipt | 22 | Service Purchase Receipt |
| 12 | Outside Process Return Receipt | 139 | Service Purchase Return Receipt |
| 134 | Outside Process Sent Receipt | 120 | Wholesale Receipt |
| 133 | Outside Process Sent Return Receipt | 3 | Return Wholesale Receipt |

**Procedure**

1. Open the receipt type list → *New*. Fill the header (Current Account, warehouse(s), date,
   document no., vehicle/driver where shown).
2. Add lines: inventory item, variant (colour/size) and quantity. Lines can be imported from an
   order or, for returns, from an earlier receipt.
3. *Save*, then **Approve** (requires `approval:approve`). *Add at least one line before approving.*
4. **Unapprove** to edit an approved receipt.
5. Optional: **Generate Serial Cards** for a receipt line; **Item Allocation** to allocate stock to
   Work Order requirements.

**Server-enforced rules (examples)**

- *Cannot receive this quantity — only N still pending (Base Unit) on this order line.*
- *Cannot return this quantity — only N still available to return (Base Unit) against this receipt line.*
- *The originating order line belongs to a different Current Account and cannot be received.*
- A receipt already on an invoice cannot be deleted: *This receipt is on invoice X — delete or relink
  that invoice first.*

### 5.2 Receipt Invoices

Menu: *Invoices* → one entry per receipt type (same 18 codes).

1. From an approved receipt, use **Create Invoice**, or create an invoice and select the receipt.
2. Several receipts **of the same Current Account** can be combined into one invoice when it is
   created (*Receipts of different Current Accounts can't be on one invoice (…)*).
3. Approve / Unapprove as above. Server-calculated fields cannot be written (*… is set by the
   server — it cannot be written directly.*).
4. A receipt can be on only one invoice (*Inventory Receipt X is already on invoice Y*).

### 5.3 Packing Lists

1. *Packing Lists* → *New*. A Work Order is mandatory (*A Work Order is required*).
2. Add lines with colour, From (Box) – To (Box) and per-size quantities. Box ranges must not overlap
   between lines (*Line 2: boxes 5–8 overlap Line 1 …*); From must be ≥ 1 and To ≥ From; sizes may
   not repeat; quantities must be non-negative.
3. **Approve** locks the packing list (*Packing list is approved — unapprove it before changing it*).

### 5.4 Serial Cards

- Generated from a receipt line, edited individually or by *assign quantity*.
- QR labels encode the URL `<application>/s/<Serial No>`. Scanning on a phone opens a mobile scan
  page after sign-in; the user needs serial-card read access.

### 5.5 Item Statement

Movement statement of an inventory item across receipts (*Item Statement* screen).

## 6. Legacy ERP — finance (operational)

*Financial Receipts* and *Receipt & Master Data* record financial receipts (FI_Receipt) with lines
and attachments. **Note:** the separate **Finance ERP** screens under `/finance-erp` (General
Ledger, Payables, Receivables, Fixed Assets) are a **demonstration only** — they keep sample data in
the browser and do not save anything.

## 7. PLM

| Area | Screens |
|---|---|
| Definitions | Style Cards, Sample Cards, Mood Boards, Swatch Cards, Product Cards, Costing Sheets, Cost Detail Entry, Costing Profit Breakdown, PLM Templates |
| General Definitions | Style Sample Types, Design Detail Types, Measurement Definitions/Charts, Department, Process, Employee, Resource, Activity Type, Color, Company, Brand, Season, Gender, Size, Route Cards, Study Templates, Sample Task Types. *Fabric Type Cards* is marked "coming soon" in the menu |
| Utilities | PLM Orders, PLM Tasks, Critical Path Chart |
| Reports | Delayed / Daily / Cancelled Task List, Sample Cost, Sample History, Analyse Cubes, plus Report Builder |
| Document Management | PLM documents |

**Style Card procedure:** *Style Cards* → *New* → style number (unique), title, season, customer,
merchandisers, sizes, colourways → *Save*. Tabs hold BOM lines, wash care, expenses, measurements and
attachments. PLM records are scoped to your **branch**.

### 7.1 Costing Sheets

1. *Costing Sheets* → *New*; link a Style or Sample Card; enter currency rates, quoted price, order
   quantity and percentages (overhead, waste, profit, commission …).
2. Fill raw-material, labour and other-cost lines; *Cost Detail Entry* and *Profit Breakdown* give
   summarised views.
3. **Lock** (`costing:lock`) freezes the sheet; **Unlock** requires `costing:unlock`. A sheet used as
   a Work Order's Initial Cost cannot be deleted. *(Lock, manual amounts and the Work Order link are
   uncommitted work in progress at audit time.)*

## 8. Docket Management

1. **Setup:** *Document Types*, *Docket Templates* (which document types a docket needs) and
   *Approval Workflows*.
2. **Dockets:** a docket is attached to a Style, Sample, Product or Order. Each docket item tracks one
   required document with a status (values used by the code: *missing*, *uploaded*, *pending*,
   *approved*, *rejected*) and the docket shows a completeness %.
3. **Adding a document:** enter the **File URL**, file name, type and version notes. The application
   stores the link only; the file itself must be hosted elsewhere.
4. **Approval Queue / Document Register:** review and approve or reject items.
5. **Sharing:** create a *Shared Link* (expires after the chosen number of days, default 30;
   optional password; can be deactivated) or an *External Review* request. Recipients open
   `/shared/<token>` without an account.
6. **Reports:** Completeness, Missing Documents, Document Expiry.

Limitations: no file upload, no watermark generation (the *watermark* option has no effect because
no watermarked copy is produced), share-link passwords are stored unencrypted — see
[07](07-Security-and-Access.md).

## 9. Reports and Report Builder

- **Standard reports** are installed by the setup scripts into each module's *Reports* menu.
- **Report Builder** (`/plm/reports`, `/legacy-erp/reports`, `/dockets/reports`): *Manage Reports*
  → design a report (data source, fields, filters) → *Preview* → save → run and **Export** as CSV,
  Excel (XLSX) or PDF.
- Permissions per module: `plm-reports`, `legacy-erp-reports`, `docket-reports` with actions
  `view`, `export`, `create`, `update`, `delete`.

## 10. BPM

*Task Queue* lists workflow tasks assigned to you; *Request Types* defines request categories. BPM
process definitions (Cutting Order Flow, Fabric Request Flow, WhatsApp Config Flow) are seeded at
API start-up.

## 11. Administration

| Screen | What it does | Permission |
|---|---|---|
| Users (*Apps → Users*, `/pages/users`) | Create, edit, deactivate users; set password; the Create User dialog lists existing roles and can assign one | `users:*`, `roles:manage` |
| Roles and role permissions | **No screen.** Creating roles and granting `module:action` permissions is only possible through the API (`POST /api/v1/roles`, `PUT /api/v1/roles/:id/permissions`) or by an administrator script. The *Permission settings* page (`/pages/permission-settings`) edits a different, CRM-level permission model and loads its role list from a placeholder route | Admin only (`system:unclassified-write`) |
| Companies (`/pages/companies`, not in the seeded menu) | Platform-owner company creates client companies, sets trial dates, sets up the first administrator (set-password e-mail link, valid 72 h by default) | Admin only |
| Menu items | Add, rename, reorder sidebar entries | `menu:*` |
| General Settings → Approval Configuration | Per-screen approval required / self-approval | `general-settings:manage-approval-configuration` |
| General Settings → Screen Parameters | Per-screen parameters | `general-settings:manage-screen-parameters` |
| Log Tracking (`/administration/log-tracking`, not in the seeded menu) | Audit log of create/update/delete/approve actions | signed-in |
| User-Defined Fields (`/administration/user-defined-fields`, not in the seeded menu) | Extra fields on screens | covered by `test:udf` |

Screens marked "not in the seeded menu" are reached by URL (`/<company-slug>/...`) until an
administrator adds them to the menu.

**Screens that look like settings but do nothing:** Currencies, Locations, Taxes, Units, SMTP
Settings, Email Templates/Signatures/Notifications, Pricing Plans, Custom Fields (template page),
Access Control, Security, Business Processes (Automation), Form Designer, Analytical Reports, Login
History. They call placeholder API routes. In particular, **SMTP must be configured through
environment variables or the `/api/v1/communication/smtp` API**, not the SMTP Settings screen.

## 12. Troubleshooting for users

| Message / symptom | Meaning | Action |
|---|---|---|
| *Insufficient permissions* | Your role lacks the `module:action` permission | Ask the administrator to grant it |
| *Password change required* | First sign-in or admin-set password | Change your password |
| *This company is not linked to a legacy ERP company…* | Company mapping missing | Administrator sets `Company.legacyCompanyId` |
| "… not found" for a record you can see elsewhere | Belongs to another company, or deleted | Check the company you are signed in to |
| *A record with the same unique value already exists* (409) | Duplicate code/number | Use a different code |
| HTTP 429 | Too many requests (rate limit) | Wait one minute |
| Generic error with an *errorId* | Unexpected server error | Give the errorId to support; it identifies the server log entry |
